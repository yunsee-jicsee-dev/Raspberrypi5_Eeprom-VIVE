# 설계와 위협 모델

## 1. 무엇을 만들었나

USB 플로피 디스켓의 원시 섹터를 LUKS 키의 보관 장소로 쓴다. 디스켓에는
파일시스템이 없고, 512바이트 섹터 단위로만 읽고 쓴다. 디스켓이 없으면
initramfs 단계에서 루트를 열 수 없으므로 부팅이 멈춘다.

"보안 부팅"이라는 말은 보통 두 가지를 뜻한다. 이 저장소는 그중 **1단계**를
구현한다.

| | 무엇을 보장하나 | 상태 |
| --- | --- | --- |
| 1단계 — 디스크 암호화 + 물리 토큰 | 토큰 없이는 **데이터를 읽을 수 없다** | 이 저장소가 구현 |
| 2단계 — Pi 5 EEPROM 서명 부팅 | 서명된 `boot.img` 만 **실행된다** | 문서만 (아래 §7) |

1단계만으로는 기밀성은 얻지만 무결성은 얻지 못한다. 둘의 차이를 §6 에서
구체적으로 적었다.

## 2. 섹터 배치 (1.44MB = 2880 × 512B)

```
LBA 0      헤더 (아래 표)
LBA 1      부팅 카운터
LBA 2      부팅 카운터 사본
LBA 3..2879  난수로 채움. 그 안에 키 조각 6개가 흩어져 있다.
```

조각은 디스크를 6구간으로 나눠 구간마다 하나씩 무작위 위치에 넣는다. 위치는
헤더의 LBA 표에만 적혀 있다. 조각이 아닌 섹터도 모두 난수이므로, 헤더를
읽지 않고는 어느 섹터가 키인지 알 수 없다.

### 헤더 섹터 (LBA 0)

| 오프셋 | 크기 | 내용 |
| --- | --- | --- |
| 0x000 | 8 | magic `VIVEFLP1` |
| 0x008 | 2 | 버전 (1) |
| 0x00A | 2 | 헤더 길이 (512) |
| 0x00C | 4 | 플래그 — bit0 PIN 필요, bit1 카운터 사용 |
| 0x010 | 16 | 토큰 UUID |
| 0x020 | 32 | salt (PBKDF2) |
| 0x040 | 4 | PBKDF2 반복 수 |
| 0x044 | 2 | 조각 개수 |
| 0x046 | 2 | 조각 하나의 길이 (32) |
| 0x048 | 128 | 조각 LBA 표 (u16 × 64) |
| 0x0C8 | 2 | 카운터 LBA |
| 0x0CA | 2 | 카운터 사본 LBA |
| 0x0CC | 8 | 생성 시각 (unix) |
| 0x0D4 | 32 | 라벨 |
| 0x1D0 | 32 | `HMAC-SHA256(salt, header[0x000..0x1CF])` |

`0x1FE` 에 `55 AA` 를 쓰지 않는다. 그래서 어떤 OS 도 이 디스켓을 FAT 으로
인식하거나 자동 마운트하지 않는다. 다른 기계에 꽂아도 "포맷하시겠습니까?"
창만 뜨고, 사용자가 수락하지 않는 한 손상되지 않는다.

헤더 MAC 의 키는 헤더 안의 salt 다. 비밀이 아니라 **손상 탐지**가 목적이다.
플로피는 자성 매체라 한 비트씩 상하는 일이 흔하고, 그걸 조용히 넘기면
엉뚱한 키가 나와 "암호가 틀렸다"는 오해를 산다. MAC 이 있으면
"LBA 1843 의 조각이 손상됨" 처럼 원인을 바로 말해 줄 수 있다.

### 조각 섹터

| 오프셋 | 크기 | 내용 |
| --- | --- | --- |
| 0x000 | 4 | magic `VSHD` |
| 0x004 | 2 | 조각 번호 |
| 0x006 | 2 | 길이 |
| 0x008 | 64 | 조각 (앞 32바이트 사용) |
| 0x048 | 32 | `HMAC-SHA256(salt, sector[0x000..0x047])` |
| 0x068 | 408 | 난수 |

### 카운터 섹터

| 오프셋 | 크기 | 내용 |
| --- | --- | --- |
| 0x000 | 4 | magic `VSEQ` |
| 0x004 | 4 | 예약 (0) |
| 0x008 | 8 | 카운터 (u64 LE) |
| 0x010 | 32 | `HMAC-SHA256(mackey, sector[0x000..0x00F])` |
| 0x030 | 464 | 난수 |

카운터의 MAC 키는 salt 가 아니라 `mackey` (§3)다. 토큰을 가진 사람만
유효한 카운터를 쓸 수 있어야 하기 때문이다.

## 3. 키 파생

```
ikm    = shard[0] || shard[1] || ... || shard[5]          (192 바이트)
pw     = HMAC-SHA256(key = ikm, msg = PIN)                (PIN 없으면 msg = "")
key    = PBKDF2-HMAC-SHA256(pw, salt, iter = 200000, 32)
LUKS 암호문 = hex(key)                                     (소문자 64자, 개행 없음)
mackey = HMAC-SHA256(key = ikm, msg = "viveboot-mac-v1")
```

설계 의도:

- **조각 전부가 필요하다.** 한 조각만 상해도 `ikm` 이 달라진다. 섹터 하나를
  덮어쓰는 사고로 토큰이 무력화되는 대신, 부분 복구 가능성을 포기했다.
  (디스켓의 신뢰성을 생각하면 백업 이미지가 실질적인 중복 장치다.)
- **PIN 은 HMAC 으로 섞고 PBKDF2 로 늘인다.** 디스켓을 훔친 사람은 20만 회
  반복을 PIN 후보마다 거쳐야 한다. 네 자리 숫자면 약 1만 번 × 0.2초 ≈ 30분
  이므로, PIN 을 쓸 거면 영문·숫자 8자 이상을 권한다.
- **`mackey` 는 `ikm` 의 일방향 함수다.** 그래서 부팅 후 검사 스크립트에
  `mackey` 만 넘겨도 LUKS 키는 새지 않는다.
- **PBKDF2 를 고른 이유**는 argon2 가 더 좋지만 initramfs 안에서
  `openssl kdf` (OpenSSL 3.0) 로 쓸 수 있는 것이 PBKDF2 라서다. 실제
  무차별 대입 방어는 토큰의 256비트 난수가 맡고, PBKDF2 는 PIN 에만 의미가
  있다.

파생식을 바꾸면 기존 토큰이 모두 무효가 된다. 그래서 파이썬 구현과 쉘 구현
양쪽에 고정 테스트 벡터를 박아 두었다 (`tests/test_token.py`
`TestKdfVectors`, `tests/test_crossimpl.sh` §6).

## 4. 두 가지 구현이 같은 값을 내야 한다

| | 쓰는 곳 | 언어 | 도구 |
| --- | --- | --- | --- |
| `tools/vive-floppy-token` | 평상시 관리 | Python 3 | `hashlib`, `hmac` |
| `lib/viveboot-common.sh` | initramfs 부팅 | POSIX sh | `dd`, `od`, `cut`, `openssl` |

initramfs 에는 파이썬이 없으므로 부팅 경로는 전부 쉘이다. 두 구현이
어긋나면 부팅이 불가능해지므로 `tests/test_crossimpl.sh` 가 같은 이미지에서
양쪽을 돌려 바이트 단위로 비교한다. 쉘이 쓴 카운터 섹터를 파이썬이 검증하는
방향도 함께 확인한다.

쉘 구현에서 주의한 점:

- MAC 검증 대상은 늘 섹터 **앞부분**이라, 16진을 다시 바이너리로 조립하지
  않고 `dd` 로 그 앞부분만 떠내 `openssl dgst -binary` 에 먹인다.
- 카운터 섹터를 쓸 때는 `printf '%b'` 로 NUL 을 내보내는 쉘별 차이를 피해,
  난수로 채운 뒤 `/dev/zero` 와 한 바이트씩 겹쳐 쓰는 방식으로 조립한다.
- `vb_le` 는 쉘 산술의 `0x` 리터럴만 쓰고 외부 명령을 부르지 않는다.

## 5. 부팅 흐름

```
cryptsetup(initramfs)
  └─ keyscript=/usr/lib/viveboot/viveboot-keyscript
       0. 우회 확인   커널 커맨드라인에 viveboot=off 가 있으면 askpass 로 exec
                      (토큰을 읽지 않고 패스프레이즈를 묻는다. 카운터도 안 올린다)
       1. 토큰 찾기   /sys/block/* 중 2880섹터급 + 헤더 magic 일치 (최대 60초 대기)
       2. 헤더 파싱   magic → 버전 → MAC → 조각 LBA 표
       3. 조각 수집   각 섹터의 magic/번호/길이/MAC 확인 → ikm
       4. PIN 입력    /lib/cryptsetup/askpass (없으면 /dev/console)
       5. 키 파생     openssl HMAC → openssl kdf PBKDF2
       6. 카운터      seq 읽고 seq+1 을 원본·사본에 기록, /run 에 기록 남김
       7. 출력        암호문을 stdout 으로, 개행 없이
```

- 0 은 `exec` 으로 askpass 에 넘긴다. 빈 출력으로 끝내는 방식은 쓰지 않는다 —
  키스크립트는 `keyscript | cryptsetup --key-file=-` 로 호출되므로 빈 출력은
  "Nothing to read on input." 으로 **실패**할 뿐이고 패스프레이즈를 묻지
  않는다. 그래서 `cryptsetup` 의 기본 대화형 경로와 똑같이 askpass 를 직접
  띄운다.
- 1~5 중 어디서든 실패하면 **아무것도 출력하지 않고** 0 이 아닌 값으로
  끝난다. `cryptsetup` 은 해제에 실패하고 initramfs 쉘로 떨어진다.
- 6 은 절대 부팅을 막지 않는다. 쓰기 금지 탭이 걸려 있거나 불량 섹터가 있어도
  경고만 남기고 진행한다. 카운터는 보조 수단이고, 못 쓴다고 해서 정당한
  사용자를 밖에 세워 둘 이유가 없다.
- `/run/viveboot` 에 남는 것: `boot-seq`(카운터 기록), `mackey`. 조각 캐시
  `ikm.cache` 는 `local-bottom` 스크립트가 `switch_root` 직전에 덮어쓰고
  지운다.

부팅 후 `viveboot-seqcheck.service` 가 `/run/viveboot/boot-seq` 와
암호화된 루트 안의 `/var/lib/viveboot/state` 를 비교한다.

| 상황 | 뜻 |
| --- | --- |
| 토큰 seq == 기록 seq | 정상 |
| 토큰 seq < 기록 seq | 되돌려진 토큰. **복제본이 쓰였을 수 있다** |
| 토큰 seq > 기록 seq | 이 토큰이 다른 기기에서 쓰였다 |
| UUID 불일치 | 다른 토큰으로 부팅했다 |
| 상태 파일 MAC 불일치 | 위조 또는 손상 |

상태 파일을 암호화된 루트 안에 두는 것이 핵심이다. 토큰만 훔친 사람은
이 기록을 고칠 수 없다. `SEQ_POLICY=poweroff` 로 두면 불일치 시 즉시 전원을
끈다 (기본은 `warn`).

## 6. 위협 모델

### 막는 것

| 공격 | 왜 막히나 |
| --- | --- |
| 기기 절도 | 루트가 LUKS 로 암호화되어 있고 키 재료는 기기 안에 없다 |
| SD/NVMe 만 떼어 복사 | 디스크에는 조각이 없다 |
| 디스켓만 절도 (PIN 사용) | PIN 당 PBKDF2 20만 회 |
| 디스켓 일부 손상 | MAC 으로 잡아내고 원인 섹터를 알려 준다 |
| 다른 OS 에 디스켓 삽입 | FAT 시그니처가 없어 자동 마운트되지 않는다 |
| 카운터 섹터 위조 | `mackey` 없이는 유효한 MAC 을 못 만든다 |

### 막지 못하는 것

| 공격 | 현실 |
| --- | --- |
| **원시 복제** (`dd if=/dev/sda of=clone.img`) | 복제본은 완전히 동등한 토큰이다. 카운터로 *사후 탐지*만 된다. 이 설계의 가장 큰 한계다 |
| **evil maid** | 부트 파티션과 initramfs 는 서명되지 않는다. 물리 접근자가 키스크립트를 바꿔 암호문을 빼낼 수 있다 → §7 |
| **동작 중 기기 탈취** | 부팅 후에는 루트가 열려 있다. 디스켓을 빼도 무관하다 |
| **루트 권한 공격자** | 열린 LUKS 키와 `/var/lib/viveboot/state` 를 모두 건드릴 수 있다 |
| **디스켓 열화** | 자성 매체는 상한다. 백업 이미지가 없으면 데이터를 잃는다 |
| **우회 플래그 주입** | `cmdline.txt` 는 평문 FAT 에 있어 물리 접근자가 `viveboot=off` 를 넣을 수 있다. 얻는 것은 패스프레이즈 화면뿐이라 기밀성은 유지된다 (아래 참고). 2요소를 지키려면 `BYPASS_CMDLINE=no` |
| **게이트 모드(평문 루트)의 모든 것** | `vive-boot-gate` 는 LUKS 없이 '토큰 없으면 부팅 중단' 만 건다. SSD 를 떼어 읽거나, `cmdline.txt` 에 `init=/bin/sh`·`break=top` 을 넣으면 그대로 통과한다 (`BYPASS_CMDLINE=no` 와 무관). 막는 것은 키보드·화면만 만질 수 있는 사람이 켜서 쓰는 것뿐이다 |
| **콜드 부트 / DMA** | 범위 밖 |

"흩어 배치"와 "난수 채움"은 *우연한 노출*과 *부분 덮어쓰기* 를 막는 장치다.
작정하고 전체를 복제하는 공격을 막지는 못한다. 그걸 막는 유일한 길은 복제할
수 없는 하드웨어(스마트카드, TPM, 보안 요소)인데, 플로피에는 없다.

### 우회 경로(`viveboot=off`)가 보안을 깎지 않는 이유

`/boot/firmware/cmdline.txt` 는 암호화되지 않은 FAT 파티션에 있다. 즉 물리
접근자가 거기에 `viveboot=off` 를 적어 토큰 요구를 끌 수 있다. 그런데 그렇게
해서 얻는 것은 **패스프레이즈를 묻는 화면**뿐이다. 토큰이 하는 일은 LUKS
키슬롯 하나를 여는 것이고, 우회는 그 슬롯을 쓰지 않고 사람이 아는 슬롯을
쓰게 하는 것일 뿐이다. 복호화에는 여전히 패스프레이즈가 필요하다.

달리 말해 이 설계에서 토큰은 **기밀성의 근원이 아니라 두 번째 요소**다.
기밀성은 LUKS 와 패스프레이즈가 들고 있다. 그래서 우회 경로를 열어 두는
비용은 "2요소가 1요소로 내려간다"이고, 그 값으로 "디스켓이 상해도 데이터를
잃지 않는다"를 산다. 토큰을 진짜 1요소로 쓰고 싶다면(= 패스프레이즈 슬롯을
아예 두지 않는다면) 디스켓 손상이 곧 데이터 손실이므로, `vive-boot-mode on`
은 토큰 외 키슬롯이 없을 때 켜기를 거부한다.

2요소 자체를 지키고 싶으면 `BYPASS_CMDLINE=no` 로 이 경로를 닫는다. 그러면
토큰을 잃었을 때의 복구는 initramfs 쉘뿐이다 (`docs/recovery.md` §4(c)).
단 물리 접근자는 `viveboot.conf` 가 들어 있는 initramfs 자체를 바꿔치울 수
있으므로, 이 닫힘은 **evil maid 를 막지 못한다** — 그건 §7 의 영역이다.

### 플로피를 쓰는 데 따르는 고유 위험

- **쓰기 수명.** 부팅마다 카운터 섹터 두 개를 쓴다. 같은 트랙을 반복해서
  쓰는 것이므로, 매일 부팅한다면 1년에 700번쯤이다. 디스켓이 상하기
  시작하면 `verify` 가 먼저 알려 준다. 수명을 아끼려면 `SEQ_UPDATE=no`.
- **쓰기 금지 탭.** 탭을 열면 카운터를 못 쓴다. 복제 탐지를 포기하고
  디스켓 보호를 택하는 선택이며, 부팅은 정상이다.
- **드라이브 의존.** USB FDD 가 고장 나면 부팅할 수 없다. 여분 드라이브를
  두거나 복구용 패스프레이즈를 준비해야 한다.

## 7. 2단계 — Pi 5 EEPROM 서명 부팅

1단계는 "토큰 없이는 읽을 수 없다"를 보장한다. "바꿔치기된 코드가 실행되지
않는다"를 보장하려면 Pi 5 의 서명 부팅이 필요하다. 그쪽은 **되돌릴 수 없는**
작업이므로 이 저장소는 자동화하지 않는다.

큰 흐름:

1. RSA-2048 키쌍을 만들고 `rpi-eeprom-digest` 로 `boot.img` 에 서명한다.
2. `rpi-eeprom-config` 로 EEPROM 에 `SIGNED_BOOT=1` 을 설정한다.
3. 공개키 해시를 OTP 에 각인한다 — **한 번 쓰면 영구적이다**.
4. 이후 그 키로 서명된 `boot.img` 만 부팅된다. 커널과 initramfs 를
   `boot.img` 안에 넣어 서명 범위에 포함시켜야 evil maid 가 막힌다.

진행하기 전에:

- OTP 각인은 되돌릴 수 없다. 서명 키를 잃으면 보드가 부팅 불가가 된다.
- 반드시 **버릴 수 있는 보드**에서 먼저 연습한다.
- 서명 키는 이 기기 밖(오프라인 매체)에 보관한다.
- 공식 문서를 그대로 따를 것:
  <https://www.raspberrypi.com/documentation/computers/configuration.html#secure-boot>

2단계를 켜면 1단계의 키스크립트도 서명 범위 안에 들어가므로, 두 단계가
합쳐져 "서명된 코드만 실행 + 토큰 없이는 복호화 불가"가 된다.
